\chapter{Experimental Setup}
\label{ch:ExperimentalSetup}

This chapter describes the datasets used for the analyses conducted in \cref{ch:metricsAnalysis} and the software tools developed to create them.
\Cref{sec:datasets} introduces the two datasets, the goodware dataset and the malware one, 
explaining why they were structured this way, 
how the entries were selected, and what their main statistical properties are.
\Cref{sec:SoftwareTools} details the two developed software tools:
the primary analysis application that downloads tarballs and computes metrics on them,
and the custom script to automatically retrieve malicious versions.

\section{Datasets}
\label{sec:datasets}

To carry out the analyses in \cref{ch:metricsAnalysis}, two datasets are required:
one to establish a baseline of normal package behavior, 
and one to evaluate whether malicious releases are detectable against it.
Accordingly, we constructed a \emph{goodware} (\cref{subsec:goodwareDataset}) and a \emph{malware} dataset (\cref{subsec:malwareDataset}).
Both consist of the same set of metrics computed from \ac{npm} tarballs,
using the tool described in \cref{subsec:ToolForAnalyzingPkgs}.
Concretely, for each package across its 20 latest releases, these datasets store:
the set of distinct file types detected, 
the total uncompressed size in bytes, 
and, in plain-text files, the length of the longest line, 
and the count of unique hexadecimal values and Ethereum addresses.
While the metrics themselves are analyzed in \cref{ch:metricsAnalysis},
this section focuses on the composition and construction of both collections.

Each dataset is organized as a collection of CSV files, one per metric.
Each is named after the metric it represents, followed by a suffix indicating the dataset: 
\texttt{\_GD} for the goodware and \texttt{\_MD} for the malware (e.g., \texttt{package\_size\_GD.csv}, \texttt{package\_size\_MD.csv}).
As illustrated in the excerpts provided in \cref{tab:csv-goodware,tab:csv-malware},
the first column provides the entry name,
followed by 20 columns, labelled -19 to 0, that hold the metric value for the corresponding release.
For the \emph{Unique Hexadecimal Values} and \emph{Unique Ethereum Addresses} metrics,
an additional filtered variant of the goodware CSV is also provided,
containing only the entries that have at least one non-zero value in any release 
(e.g., \texttt{unique\_hexadecimal\_values\_GD\_GreaterThan0.csv}).
This filtered file is used in \cref{ch:metricsAnalysis} to focus the analysis on modules that are actually informative for those metrics.
The CSV format was chosen for three main reasons: 
it is human-readable without specialized software, 
it integrates naturally with data analysis libraries such as \texttt{pandas}~\cite{pandas} and \texttt{matplotlib}~\cite{matplotlib},
and it enables independent reuse of the datasets without requiring any specific environment.
Both datasets are publicly available on
GitHub\footnote{\url{https://github.com/Frazzerz/Datasets-npm-Analysis}}.

A key design decision shared by both is the fixed window of exactly 20 releases per entry.
This constraint ensures comparability across packages and between datasets,
and reflects the deliberate methodological choice of tracking the evolution of each 
across consecutive releases rather than analyzing a single snapshot in isolation.
The threshold of 20 was chosen to balance two competing requirements,
as it is sufficiently large to capture a meaningful historical trend
while remaining small enough to retain a large fraction of the ecosystem.
A higher threshold would have excluded significantly more packages from the goodware dataset.
This longitudinal perspective is essential to the detection approach,
because malicious updates stand out as sudden deviations from an otherwise predictable evolutionary pattern, 
a signal that would be invisible in a single-snapshot analysis.
However, this represents a trade-off and a limitation, as for long-lived projects with many releases, 
examining the 20 most recent versions may capture a partial view of their history, 
omitting behavioral patterns present in the early stages of development.

\subsection{Goodware Dataset}
\label{subsec:goodwareDataset}

The purpose of the goodware dataset is to establish a \emph{baseline}, 
the typical behavior of each metric under normal, benign development conditions.
This baseline is used in \cref{ch:metricsAnalysis} to identify packages exhibiting outlier values
and to evaluate whether the compromised releases in the malware dataset are detectable.

To build a large and representative baseline, 
the dataset is composed of modules ranked among the 1,000 most popular in the \ac{npm} registry by number of stars, 
according to a publicly available popularity ranking~\cite{tristan2026listtop10000}.
This criterion was chosen because such packages are the most realistic and impactful targets of \acp{SSCA}.
Of the 1,000 candidates, 371 have fewer than 20 releases available in the registry and were therefore excluded, 
as the analysis requires exactly that number per entry.
The dataset includes the remaining 629 packages, 
using the 20 most recent versions parsable via node-semver~\cite{semver} (ensuring chronological order).
Within the CSV file, entries are sorted by descending order of popularity,
so that the most downloaded modules appear first.
The developed tool (\cref{subsec:ToolForAnalyzingPkgs}) downloads the corresponding tarballs automatically,
taking as input a json file containing the 1,000 names 
extracted from the same ranking~\cite{tristan2026listtop10000}.

The 629 packages in the dataset span a wide range of sizes and complexities,
reflecting the diversity of real-world \ac{npm} ecosystem.
\Cref{tab:goodware-stats} summarizes the key statistical properties of the goodware dataset for each of the five metrics analyzed in \cref{ch:metricsAnalysis}.
For each, the table reports the median and maximum values, 
the number of packages that have at least one non-zero value across their versions (Packages~>~0), and representative notable examples.

For \emph{File Types}, the median and maximum refer to the number of unique file types found per release.
The maximum of 27 is attributable to \texttt{moment-timezone} (in version 0.5.36),
which erroneously included an unrelated temporary folder, subsequently removed in the following version, as discussed in \cref{sec:analysisFileTypes}.
In the Notable examples column, the three most common extensions are reported,
together with the percentage of packages that contain at least one file of that type.

For \emph{Package Size}, the median grows progressively over time, 
from approximately 71~KB in older releases to 84~KB in the most recent ones.
The maximum of 211~MB corresponds again to \texttt{moment-timezone}, 
for the same reason described above and also detailed in \cref{sec:analysisPackageSize}.
Other packages with notably large sizes include \texttt{next} and \texttt{aws-sdk},
which are consistently among the largest across all their versions.

The high variability in \emph{Longest Line Length} is attributable to the presence of build artifacts in some tarballs.
The maximum of 4,041,545 characters belongs to \texttt{next},
for this reason, similarly to those under the \texttt{@angular} scope, as detailed in \cref{sec:analysisLLL}.

For \emph{Unique Hexadecimal Values}, 109 out of 629 packages (17.3\%) have at least one hexadecimal value in any version; 
the remaining 520 have none.
Among those with non-zero values, the ones with the highest counts are typically encryption-related,
such as \texttt{crypto-js} and \texttt{node-forge}, or contain generated JavaScript files, such as \texttt{aws-sdk}.
The maximum of 2,208 belongs to \texttt{polished}, 
which temporarily included an erroneous \texttt{.yarn} cache directory with a generated file, as detailed in \cref{sec:analysisHex}.

For \emph{Unique Ethereum Addresses}, only two packages (\texttt{brace-expansion} and \texttt{dotenv-expand})
contain a single address each, across their versions.
In both cases, the address originates from a \texttt{tea.yaml} protocol registration file unrelated to the core functionality of either module, 
as discussed in \cref{sec:analysisEthAdd}.

The main limitation of this dataset is that it represents only popular packages; 
less prominent ones may exhibit different statistical properties, and the baselines derived here should be interpreted accordingly.

\subsection{Malware Dataset}
\label{subsec:malwareDataset}

The malware dataset contains packages compromised by one of the four \acp{SSCA} analyzed in \cref{ch:AnalysisRecentAttacks},
and is used in \cref{ch:metricsAnalysis} to evaluate whether the metrics are sensitive enough to detect the anomalous malicious releases.
The dataset includes twenty entries, each analyzed across exactly 20 releases: nineteen legitimate and one compromised.
Within the CSV files, packages are ordered chronologically by attack: the three from Attack~A appear first,
followed by the nine from Attack~B, the four from Attack~C, and the four from Attack~D.
The nineteen legitimate versions were downloaded automatically by the tool described in \cref{subsec:ToolForAnalyzingPkgs},
while the malicious tarballs were retrieved separately using the custom script presented in \cref{subsec:DownloadMaliciousTarballs}.

The twenty packages were selected based on two criteria.
The first was the availability of at least nineteen legitimate prior versions in the registry,
as required by the longitudinal analysis design.
The second was a sufficiently high weekly download count to reflect realistic, high-impact attack scenarios.
Entries that did not satisfy the first criterion were therefore excluded;
specifically, two from Attack~A and nine from Attack~B lacked enough prior versions.
For Attacks~C and~D, which affected a very large number of packages (187 and 1,055, respectively),
including all compromised ones would not add analytical value and would make the dataset difficult to manage;
therefore, only a representative subset was included, 
selecting those with at least 1,000 weekly downloads.
It is worth noting that all nine packages included from Attack~B are among the 1,000 most popular in the registry, 
while none of those from the remaining attacks fall into that category.

The full list of entries included in the malware dataset, 
together with the specific compromised release number for each, is reported below.

    \item Attack~B (\cref{sec:attackB}):

        \item \texttt{ansi-styles}, v.6.2.2
        \item \texttt{chalk}, v.5.6.1

        \item \texttt{color-string}, v.2.1.1
        \item \texttt{debug}, v.4.4.2
        \item \texttt{supports-color}, v.10.2.1
        \item \texttt{strip-ansi}, v.7.1.1
        \item \texttt{wrap-ansi}, v.9.0.1
    \end{itemize}
    \item Attack~C (\cref{sec:attackC}):
        \begin{itemize}

\Cref{tab:csv-malware} presents an excerpt of \texttt{package\_size\_MD.csv} with one entry per attack, 
illustrating how the malicious version appears in the malware dataset.
As observed in \cref{tab:csv-malware}, for the \emph{Package Size} metric, 
the compromised release in all \acp{SSCA} introduces a sharp, 
isolated spike surrounded by otherwise predictable evolutionary patterns in the legitimate values.
For \texttt{eslint-config-prettier} and \texttt{chalk}, the value at version 0 returns to the pre-attack level 
because the maintainer republished the last clean release, as discussed in \cref{subsec:goodwareDataset}.
Instead, for \texttt{@asyncapi/bundler}, the spike falls at version 0, 
because the \ac{PM} chose to downgrade to the prior version rather than republishing it as a new one, as described in \cref{sec:npmEcosystem}.

The main limitation of this dataset is that it covers a narrow selection of attack campaigns;
packages compromised by different \acp{SSCA} may exhibit structural properties not captured by this sample,
and the results should be interpreted accordingly.
