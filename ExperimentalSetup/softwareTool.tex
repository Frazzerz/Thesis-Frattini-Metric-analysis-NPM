\section{Software Tools}
\label{sec:SoftwareTools}

This section describes the tool and script developed to create the two datasets presented in \cref{sec:datasets}.
\Cref{subsec:ToolForAnalyzingPkgs} presents the primary analysis application, namely \texttt{npm Packages Analyzer},
while \cref{subsec:DownloadMaliciousTarballs} details the custom script to automatically retrieve malicious versions from mirror registries.

\subsection{The npm Packages Analyzer}
\label{subsec:ToolForAnalyzingPkgs}

The developed tool computes the metrics analyzed in \cref{ch:metricsAnalysis} from a set of \ac{npm} package releases.
It enables the construction of both the goodware (\cref{subsec:goodwareDataset}) and the malware dataset (\cref{subsec:malwareDataset}).
Implemented in Python, it is available on GitHub\footnote{\url{https://github.com/Frazzerz/npm-packages-analyzer}},
and can be invoked from the command line as follows:
\begin{verbatim}
python3 main.py --json <input_file>.json [--workers N] [--local]
\end{verbatim}

The required input is a json file containing the list of \ac{npm} package names to analyze. 
The optional \texttt{-{}-local} flag allows local tarballs,
such as the malicious releases in the malware dataset, 
to be included alongside those downloaded from the registry.
The optional \texttt{-{}-workers} flag controls the number of parallel processes used for per-file metric computation. 
Packages and their versions are processed sequentially (from oldest to most recent), 
while the analysis of individual files within each version is parallelized using multiprocessing. 
The tool workflow is organized into four phases, described below.

\subsubsection{Phase 1: Version Retrieval}
\label{subsubsec:ToolForAnalyzingPkgsPhase1}

The \texttt{npmClient} component queries the official \ac{npm} registry to retrieve the module metadata and the list of all available releases. 
From this list, only versions parsable by node-semver~\cite{semver} are kept, 
so that they can be sorted chronologically. 
For the goodware dataset (\cref{subsec:goodwareDataset}), the 20 most recent valid versions are selected and their tarballs downloaded. 
For the malware dataset (\cref{subsec:malwareDataset}), only the nineteen most recent legitimate versions are fetched; 
the twentieth slot is reserved for the malicious tarball, 
which is retrieved separately via the custom script (\cref{subsec:DownloadMaliciousTarballs}) and included through the \texttt{-{}-local} flag.

\subsubsection{Phase 2: Metrics Computation}
\label{subsubsec:ToolForAnalyzingPkgsPhase2}

For each version, the tool first extracts the tarball and computes the metrics on the individual files it contains. 

The \emph{File Types} metric (\cref{sec:analysisFileTypes}) is computed by running \texttt{Magika}~\cite{magika}, 
a deep-learning-based content-type detection library developed by Google. 
Each file in the tarball is processed, and the resulting label is recorded.
Notably, \texttt{Magika} labels Windows \ac{PE} files (including \acp{DLL}) as \texttt{pebin}.
The \emph{Package Size} metric (\cref{sec:analysisPackageSize}) is computed as the uncompressed size in bytes of each individual file.

Metrics based on the textual content of files, namely \emph{Longest Line Length} (\cref{sec:analysisLLL}), 
\emph{Unique Hexadecimal Values} (\cref{sec:analysisHex}), 
and \emph{Unique Ethereum Addresses} (\cref{sec:analysisEthAdd}),
are computed only on plain-text sources, such as JavaScript and TypeScript, 
and are therefore skipped for binary formats such as zip, png or \ac{DLL}.
To determine the nature of each item and thereby distinguish plain-text from binary content, 
the tool uses \texttt{Magika} to classify each entry and checks the detected label against a predefined whitelist of allowed types.
Additionally, for these metrics, 
comments are stripped from JavaScript and TypeScript code before computation, 
using a parser from the \texttt{tree-sitter} library~\cite{treesitter}, so that comment content does not affect the results.
To compute \emph{Longest Line Length}, the tool splits the buffer at newline characters and records the length of the longest line.

The \emph{Unique Hexadecimal Values} and \emph{Unique Ethereum Addresses} metrics are computed via regular expressions (regex).
These are precompiled with \texttt{re.compile} from the Python \texttt{re} library~\cite{re}, 
which parses each pattern once and reuses the resulting object across all files, reducing overhead.
The precompilation step also allows flags to be specified at compile time; 
for example, \texttt{re.IGNORECASE} is used to match both \texttt{0x} and \texttt{0X} prefixes in the hexadecimal logic, 
making the search case-insensitive.
To find all matches within a file contents, the tool uses the \texttt{finditer} method on the compiled object,
which returns an iterator over all matches and is more memory-efficient than collecting all results at once.

The regex used for \emph{Unique Hexadecimal Values} (\cref{sec:analysisHex}) is: \verb|_?0x[0-9a-fA-F]+|

The optional leading underscore (specified with \texttt{\_?}) captures the naming convention used by obfuscation
tools when a hexadecimal token serves as a variable or function name (e.g., \texttt{\_0x6fd57a}), 
followed by the mandatory \texttt{0x} prefix with one or more hexadecimal characters (digits 0 to 9 and letters a to f, both lowercase and uppercase).
This flexible matching rule allows capturing values even when they appear inside function calls or other code structures, 
where strict boundaries, would miss them.

For \emph{Unique Ethereum Addresses} (\cref{sec:analysisEthAdd}), the pattern is instead: \\
\verb|(?<![\w\-/_])0x[a-fA-F0-9]{40}(?![\w\-/_])|

A valid Ethereum address consists of the prefix \texttt{0x} followed by exactly 40 hexadecimal characters~\cite{ethereum}.
The lookbehind (\texttt{(?<![{\textbackslash}w{\textbackslash}-/\_])}) 
and lookahead (\texttt{(?![{\textbackslash}w{\textbackslash}-/\_])})
prevent matching strings embedded in URLs, file paths, or longer hexadecimal sequences, 
which standard word boundaries like \texttt{{\textbackslash}b} would not correctly handle, 
given the presence of typical path separators such as slashes and hyphens.

Once per-file metrics are available, they are aggregated to produce a single version-level summary. 
For \emph{File Types}, the per-file labels are collected into a deduplicated set of unique types. 
For \emph{Package Size}, the per-file sizes are summed. 
For \emph{Longest Line Length}, the maximum across all plain-text files is taken. 
For \emph{Unique Hexadecimal Values} and \emph{Unique Ethereum Addresses}, the per-file match lists are merged and deduplicated.

\subsubsection{Phase 3: Results Saving}
\label{subsubsec:ToolForAnalyzingPkgsPhase3}

For each package, results are saved incrementally to two CSV files as each version is processed, 
so that partial outputs are preserved in the event of an interruption or error.
\texttt{file\_metrics.csv} records one row per file across all analyzed releases, 
with columns for each per-file metric, as illustrated in \cref{tab:file-metrics-excerpt},
while \texttt{aggregate\_metrics\_by\_single\_ \allowbreak version.csv} records one row per release, 
with columns for the corresponding version-level aggregated values, as shown in \cref{tab:aggregate-metrics-excerpt}.
Furthermore, a \texttt{log.txt} file is saved, updated incrementally, mirroring the terminal output.
It reports general information such as the total number of packages and worker count, 
and for each entry it logs the number of versions found, 
the download status of each tarball, the per-release analysis progress, and the total analysis time.

\subsubsection{Phase 4: Dataset Generation}
\label{subsubsec:ToolForAnalyzingPkgsPhase4}
Once all packages have been analyzed, the dataset files are produced by running:

\begin{verbatim}
python3 dataset.py 
\end{verbatim}

This script reads the \texttt{aggregate\_metrics\_by\_single\_version.csv} file from every analyzed package 
and generates a separate CSV file per metric, where each row corresponds to an entry and each column to one of its analyzed versions,
as illustrated in \cref{tab:csv-goodware,tab:csv-malware}.
Each resulting file contains the metric values for every version of every analyzed package, 
collectively forming the datasets described in \cref{sec:datasets}.
