\section{Analysis Metric 5: Unique Ethereum Addresses}
\label{sec:analysisEthAdd}

The fifth and final metric is the count of unique Ethereum addresses found across all
plain-text files of an \ac{npm} package version.
It was motivated by Attack~B (\cref{sec:attackB}),
in which the malicious code embeds seven known smart contract Ethereum addresses to perform cryptocurrency transaction hijacking.
The intuition is that Ethereum addresses are essentially absent from general-purpose \ac{npm} packages, 
so even a small count would constitute an anomalous signal.

Each cryptocurrency defines its own address format, so this metric cannot be generalized across all currencies.
We initially considered extending the analysis to Bitcoin addresses and their variants,
generalizing this metric to \emph{Unique Cryptocurrency Addresses}, 
but doing so produced a non-negligible number of false positives in the goodware dataset,
as legitimate \ac{npm} packages may contain strings that match the Bitcoin address format without being actual addresses.
For instance, repeated digit sequences used as numerical constants or for testing purposes, 
such as \texttt{11111111112222222222333333333344}, 
are found in packages like \texttt{aws-sdk} across all their analyzed versions.
Since Bitcoin addresses are not associated with any of the four \acp{SSCA} analyzed in this research, 
and no reliable library or regex rule was found capable of disambiguating true addresses from these coincidental matches,
we chose to restrict the metric to Ethereum only, whose format is unambiguous, as shown in \cref{subsec:goodwareEthAdd}.
This specificity is both a strength and a limitation, 
as it provides a reliable signal for attacks targeting Ethereum-based wallets, 
but offers no coverage for \acp{SSCA} that abuse other cryptocurrency ecosystems.

\subsection{Analysis of the Goodware Dataset}
\label{subsec:goodwareEthAdd}

For this metric, the goodware dataset provides the count of unique Ethereum addresses
found in each of the 20 analyzed versions of every package,
as described in \cref{subsec:goodwareDataset}.
The distribution is so sparse that a trend figure is uninformative,  
and, across all 629 packages, only two contain at least one Ethereum address in a given version, 
namely \texttt{brace-expansion} and \texttt{dotenv-expand}, as also summarized in \cref{tab:goodware-stats}.
Both cases are analyzed below to understand the reason for this presence.

\textbf{brace-expansion} provides shell-like brace expansion for JavaScript~\cite{brace-expansion}.
Starting from version 4.0.0 (the second-to-last available release),
the tarball includes a file named \texttt{tea.yaml},
a configuration file required to register a project on the Tea protocol.
The Tea protocol is an incentivization system for open-source projects that allows
registered packages to earn TEA tokens proportional to their popularity and usage~\cite{teaProtocol}.
The \texttt{tea.yaml} file must include one or more Ethereum addresses
to receive tokens and to define the identities of the project owners.
This file is also present in the latest available version (4.0.1).

\textbf{dotenv-expand} extends the functionality of \texttt{dotenv} 
by allowing variable expansion in \texttt{.env} files~\cite{dotenv-expand}.
Similarly to \texttt{brace-expansion},
starting from version 11.0.7 the tarball includes a \texttt{tea.yaml} file containing one Ethereum address.
This file remained present for four consecutive releases,
until version 12.0.3 (the most recent available), in which it was removed.

These two cases establish that the presence of even a single Ethereum address
in an \ac{npm} tarball is rare in the goodware dataset,
and limited to a specific optional configuration file related to a third-party incentivization protocol, 
with no connection to the core functionality of the packages.

\subsection{Comparison with the Malware Dataset}
\label{subsec:analysisEthAddComparisonMalware}

Given that only two packages in the goodware dataset contain one Ethereum address,
the appearance of seven of them in the compromised versions of Attack~B represents an important outlier.
Because this is a value with no precedent in the goodware baseline, the metric is effective for detecting this specific attack.

Otherwise, the metric is not indicative for the remaining three attacks.
For Attack~A (\cref{sec:attackA}), the malicious \ac{DLL} is a binary file and is excluded from the computation, 
leaving the address count unchanged.
For Attacks~C and~D (\cref{sec:attackC,sec:attackD}),
the malicious goal is credential and token exfiltration, not cryptocurrency theft;
neither \texttt{bundle.js} nor \texttt{bun\_environment.js} contains any Ethereum addresses,
so the count remains at zero as in the legitimate versions.

This metric is therefore highly specific, 
as it detects the class of \ac{SSCA} that target cryptocurrency wallets
and provides no signal for other attack categories, making it a limited but reliable metric.
