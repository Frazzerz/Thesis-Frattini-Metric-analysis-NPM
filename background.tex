In this chapter, we provide the fundamental information regarding \ac{SSC}, the 
\acp{SSCA}, the \ac{NPM} ecosystem and the tarballs.

\section{Software Supply Chain and Software Supply Chain Attacks}
\label{sec:SSCAndSSCA}

Developers tend to use ready-made software components in their projects 
for common functionalities, such as date parsing, HTTP request handling, or \ac{UI}, 
rather than implementing them from scratch.

These software components are called dependencies, 
and these dependencies in turn can depend on other components, 
thus constituting a \ac{SSC} \cite{ohm2023sok}.

These components or packages are distributed in Open Source Package Repositories such as \ac{NPM}, \ac{PyPI} and RubyGems.

These repositories are often used to carry out attacks,
as they are open and decentralized systems where anyone can freely publish a package \cite{ohm2020backstabbersknifecollectionreview}. 
An attacker may inject malicious code into a legitimate package update, in order to compromise 
in this way all projects and packages that depend on it.

This type of attack on the \ac{SSC} is called \ac{SSCA} and has become 
increasingly common in recent years \cite{ohm2020backstabbersknifecollectionreview}.

Several attack vectors are possible \cite{duan2020measuringsupplychainattacks},
such as Account Compromise, which refers to compromising accounts of Package Maintainers 
(those who develop and manage the packages) on the registry portal (like \ac{NPM}), allowing
the attacker to release malicious versions.

In \acp{SSCA} the victims are developers and users.
Developers can be exploited 
directly to steal their credentials or damage their infrastructure,
and indirectly as a channel to reach users through their applications 
or services. Users can be exploited to steal their credentials or damage their devices.

Attackers often attempt to mask their malicious code using obfuscation techniques to
prevent visual detection \cite{ohm2020backstabbersknifecollectionreview}.
The most common technique is to use a different encoding, such as hexadecimal,
to hide function or variable names, renaming them with names devoid of semantic meaning, like \_0x264994.
The leading underscore is inserted because in JavaScript,
and in other programming languages, variable or function names cannot start with a number.
In the malicious code, however, there are also hexadecimal values without this prefix, 
used for example to simply represent numbers and constants.
This approach is simple and effective, as it does not require the use of external dependencies.

\section{NPM Ecosystem}
\label{sec:NPMEcosystem}

All the information regarding \ac{NPM} reported below has been taken from the official documentation \cite{npmdocs2026npmdocumentation}.

For the JavaScript and Node.js ecosystem, \ac{NPM} is one of the largest and most active Open source package repositories, 
with over two million packages available \cite{9505063}.

The public \ac{NPM} registry is a database of JavaScript packages, where developers 
can share and download packages. % https://docs.npmjs.com/about-the-public-npm-registry

A package is a folder containing various files
that can be borrowed for use in own projects.
% https://docs.npmjs.com/cli/v11/commands/npm-install
% https://docs.npmjs.com/about-npm

To resolve packages by name and version, \ac{NPM} communicates with the public registry
(configured by default at \href{https://registry.npmjs.org}{https://registry.npmjs.org}), from 
which allows users to retrieve any version of a package currently available in the registry. 
% https://docs.npmjs.com/cli/v11/using-npm/registry

A \ac{NPM} tarball is a gzipped package,
the standard format used when packages are uploaded to a registry, and 
represents a package at a specific version.
Instead, a Git URL refers to a package in a Git repository. 
% https://docs.npmjs.com/cli/v11/using-npm/package-spec
% https://docs.npmjs.com/cli/v11/commands/npm-install

The content of the tarball may differ from the content of the Git repository, even though both represent the same package.
%https://docs.npmjs.com/cli/v11/commands/npm-publish
%https://docs.npmjs.com/cli/v11/configuring-npm/package-json

In fact, through the optional "files" field of package.json, 
it is possible to include only the specified files, or exclude them if the .npmignore file is present.

Therefore, to ensure a fair and symmetrical comparison, it is necessary to analyze the same type of artifact.

\section{Tarball content}
\label{sec:tarballContent}

A tarball can contain any type of file, however, 
the following types of files are typically found within it \cite{pinckney2023largescaleanalysissemantic}:

\begin{itemize}
    \item \textbf{Configuration files and Metadata:}
    
    The package.json file describes the package's file or directory, 
    and a package must contain a package.json file in order to be published to the \ac{NPM} registry.
    %https://docs.npmjs.com/about-packages-and-modules
    
    In package.json, the name and version fields are required, and together they form an identifier that is assumed to be completely unique.
    %https://docs.npmjs.com/cli/v11/configuring-npm/package-json

    Once a package is published with a given name and version, that specific combination can 
    never be used again, even if it is removed with command \texttt{npm unpublish}.
    This is the reason why it is impossible to overwrite malicious versions once they have been released.

    Other common optional fields include the description, license, repository and dependencies
    on other packages.
    It is important to note that specifying a reference (a link) 
    to a GitHub repository for a package is optional.

    \textcite{duan2020measuringsupplychainattacks} highlight that this lack of mandatory 
    link represents a significant security gap because it prevents registries from verifying 
    that the distributed package actually matches its public source code, allowing attackers to inject malicious 
    code during the publication phase without detection.
    
    \item \textbf{Documentation and general information:}

    Frequently, documentation files, 
    such as Markdown files like README.md and CHANGELOG.md, and the LICENSE text file 
    used to specify copyright, are included inside the tarball.

    \item \textbf{Code files and Build Artifacts:}

    The tarball generally includes JavaScript and/or TypeScript code files, 
    which constitute the functional logic of the package.

    Build artifacts are often found within the tarball \cite{9240695}.
    These files are the final product of the transformation and compilation process of a package's source code.
    They are optimized versions of the original code automatically generated, rather than written directly by developers.

    Through processes such as minification, these artifacts reduce the size of the files
    and improving application performance.

    Furthermore, this also ensures compatibility, as the code transformation during the build allows the software to run 
    across different environments and runtimes without the end user needing to worry about the original syntax.

    Since the \ac{NPM} ecosystem is permissive, there is no standardized
    way to distinguish if a package contains build artifacts or where they are located.
    While common conventions suggest that folders such as \texttt{dist/}, 
    \texttt{build/} or \texttt{lib/} contain artifacts, 
    this structure is neither guaranteed nor verifiable a priori, as it depends entirely on the developer's choices.

\end{itemize}
